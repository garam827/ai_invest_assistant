This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Backend modules: `drive_db.py`, `data_fetcher.py`, `signal_engine.py`, `news_fetcher.py`, `openrouter_briefing.py`, `recommendation_engine.py`, `telegram_notifier.py`, `chart_builder.py`, `report_builder.py`, `paper_trading.py`, `config.py`. The Streamlit UI ([기능 4]) is a single page (`app.py`, no top-level `st.title` — deliberately removed) split into six `st.tabs`: **소개** (about-the-program / Tom Basso philosophy blurb + the indicator glossary table — no analysis functionality, purely reference), **대표 자산군 분석** (asset-class trend analysis across 12 tickers in 6 categories — see Architecture below), **종목 차트 (S&P 500)** (per-ticker candlestick + signal chart), **데이터 적재** (the manual data-collection trigger — originally tab 1, moved as more tabs were added), **리포트 히스토리** (browse past daily reports stored in Drive, added in v3.0), and **모의 투자** (manual paper-trading positions + live P&L, added in v3.21 — see `paper_trading.py`). Deliberately a single page, not a multipage `pages/` app (removed by request). The all-tickers signal scan table and the chat tab are not built.

**Automation is live** ([기능 5]): GitHub Actions (`.github/workflows/collect.yml` + `recommend.yml`, chained via `workflow_run`) replaced the originally-planned GCP Cloud Run/Cloud Scheduler (abandoned over billing-account friction). `collect.yml` runs `python data_fetcher.py update` on a weekday cron; on success, `recommend.yml` runs `python recommendation_engine.py`, which generates 매수/HOLD/매도 calls for `ASSET_CLASS_TICKERS` only (not all 503 S&P 500 tickers — keeps LLM/news usage bounded), builds a combined daily HTML report (`report_builder.py`) that it commits to `docs/reports/{date}.html` for GitHub Pages to serve publicly, and sends a Telegram summary + report link. The "데이터 적재" tab's button remains as a manual, on-demand alternative to the collect cron. There is no test suite or lint config yet — when one is added, update this file with the actual commands.

Setup: `pip install -r requirements.txt`, copy `.env.example` to `.env` and fill in `DRIVE_FOLDER_ID` / `GOOGLE_OAUTH_CLIENT_SECRET_PATH` / `OPENROUTER_API_KEY` / `EXA_API_KEY` (see [GOOGLE_DRIVE_SETUP.md](GOOGLE_DRIVE_SETUP.md) for the Drive OAuth setup) and optionally `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` (see [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md) — daily recommendation notifications, cron-only). `data_fetcher.py` is runnable directly: `python data_fetcher.py init` (5y backfill of S&P 500 + asset-class tickers, run once), `python data_fetcher.py update` (S&P 500 membership sync + daily append + asset-class update, the intended cron command — same as `data_fetcher.run_full_collection`), or `python data_fetcher.py sync` (S&P 500 membership reconciliation only). All 503 current S&P 500 tickers plus all `ASSET_CLASS_TICKERS` have already been backfilled into the live Drive folder. Run the UI with `streamlit run app.py`. To deploy the UI publicly, see [GCP_Setyo_Guide.md](GCP_Setyo_Guide.md) (GCP Compute Engine + Docker Compose — the adopted path, v3.15; `docker-compose.yml`/`Dockerfile`/`.dockerignore` already in the repo root). [GCP_STREAMLIT_DEPLOY.md](GCP_STREAMLIT_DEPLOY.md) (Cloud Run) is kept as an untested alternative.

## What this project is

A Tom Basso-style ("Mr. Serenity") trend-following investment assistant chatbot: a rule-based, ATR-driven trend-following signal and position-sizing engine wrapped in an LLM chat interface, applied to both individual S&P 500 stocks and representative asset-class proxies (equities, crypto, precious metals, bonds, commodities). Full spec (versioned, latest first): [investment_assistant_spec.md](investment_assistant_spec.md).

## Architecture

- **Frontend / Chat UI**: Streamlit, single page (`app.py`) with `st.tabs` separating features (not a multipage `pages/` app — everything runs in one process/session so tabs share `st.cache_resource`/`st.cache_data` state directly)
- **Data source**: yfinance (Yahoo Finance API) — daily OHLCV for all S&P 500 tickers plus `data_fetcher.ASSET_CLASS_TICKERS` (12 tickers across 6 categories: 주식 `SPY`/`QQQ`, 암호화폐 `BTC-USD`, 귀금속 `GLD`, 채권 `TLT`/`IEF`, 원자재 `DBC`/`USO`/`UNG`/`DBA`/`DBB`, 통화 `UUP`). News for the LLM recommendation flow comes from the **Exa search API** (`news_fetcher.fetch_ticker_news_exa`), not yfinance — see below.
- **"Database"**: Google Drive API storing one Apache Parquet file per ticker (`[Ticker].parquet`), accessed via OAuth user credentials (not a service account — the GCP project enforces `iam.disableServiceAccountKeyCreation`, see [GOOGLE_DRIVE_SETUP.md](GOOGLE_DRIVE_SETUP.md)) — see `drive_db.DriveDB`. Also stores small JSON metadata files: `_universe.json` (S&P 500 active/inactive tickers + sectors + descriptions), `_news_{YYYY-MM-DD}.json` (per-date news archive, see below), and `_recommendations_{YYYY-MM-DD}.json` (daily cron recommendation results).
- **LLM engine**: OpenRouter (default model `nvidia/nemotron-3-ultra-550b-a55b:free`, configurable via `OPENROUTER_MODEL_NAME`) — see `openrouter_briefing.py`. Switched from Vertex AI/Gemini for cost reasons (see spec changelog). The buy/hold/sell **action** itself never depends on the LLM (see Core signal & sizing logic below) — the LLM only adds narrative explanation on 매수/매도 days.
- **Infra**: GitHub Actions (`.github/workflows/collect.yml` + `recommend.yml`, chained via `workflow_run`) — see Data flow below. Originally planned as GCP Cloud Run + Cloud Scheduler, abandoned over a billing-account blocker.
- **Report hosting**: GitHub Pages, serving the repo's `docs/` folder (`https://garam827.github.io/ai_invest_assistant/`) — `recommend.yml` commits the day's `report_builder.py`-generated HTML into `docs/reports/{date}.html`. No separate hosting account/billing needed since it's the same repo already used for GitHub Actions.
- **Notifications**: Telegram (`telegram_notifier.py`), cron-only — see [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

### Module map

- `config.py` — all tunables/secrets, loaded from `.env`. Every other module reads from here rather than hardcoding constants.
- `drive_db.py` — `DriveDB` class: Drive OAuth user auth (browser consent on first run, cached to `token.json` thereafter), per-ticker Parquet find/download/upload, `upsert_ticker` (concat + `drop_duplicates` by Date + re-upload), generic `load_json`/`save_json` for small metadata files (used for the ticker universe and the news archive, see below), `load_text`/`save_text` (v3.0, same pattern for the HTML daily report), and `list_filenames(prefix)` (v3.0, lists Drive filenames starting with a prefix — used to enumerate saved report dates).
- `data_fetcher.py` — S&P 500 ticker list (scraped from Wikipedia via `requests` + a browser User-Agent, since Wikipedia 403s the default urllib UA — parsed with `pd.read_html(io.StringIO(...))`), yfinance OHLCV fetch, `run_initial_ingestion` (5y backfill), `sync_universe` (reconciles S&P 500 membership changes, see Data flow below), `run_daily_update` (delta fetch + upsert for the active S&P 500 universe), `run_asset_class_update` (same delta-fetch logic, applied to the fixed `ASSET_CLASS_TICKERS` dict — independent of S&P membership), `run_full_collection` (all three, in order — what the "데이터 적재" tab and `python data_fetcher.py update` both run). `_update_one_ticker` is the shared per-ticker delta-fetch-and-upsert helper both `run_daily_update` and `run_asset_class_update` call. `ASSET_CLASS_TICKERS` is `{ticker: {"label": display_name, "category": category, "description": one_liner, "news_query": macro_query}}` — categories: 주식/암호화폐/귀금속/채권/원자재/통화 (`UUP`, v3.20). `news_query` (v3.3) is an English macro-oriented search phrase used instead of the ticker for Exa news lookups — `"GLD stock news"` mostly surfaces "GLD down X%" wire blurbs, not the macro drivers behind the move, so proxies search under the underlying asset's name instead (e.g. `"gold price outlook macro drivers analysis"` for GLD). `sync_universe` also builds a `{ticker: "회사명 (GICS 세부업종)"}` description map from the same Wikipedia table (no extra requests) and writes it into `_universe.json`'s `descriptions` key for all active S&P 500 tickers. CLI entry point via `if __name__ == "__main__"` with `init`/`update`/`sync` modes.
- `signal_engine.py` — pure pandas, no I/O, and ticker-agnostic (same functions work on S&P stocks or asset-class tickers). Donchian channel, Wilder ATR, Bollinger Bands (reference-only, not part of the entry/exit rules), Ichimoku Kinko Hyo (`calculate_ichimoku`, v3.16 — Tenkan/Kijun/displaced Senkou A·B/Chikou, plus undisplaced `_Raw` Senkou columns consumed only by `chart_builder.py` for the future cloud tip; reference-only, same as BB), trailing stop, volume-surge filter, position sizing, `Buy_Trigger`/`Sell_Trigger` (first-occurrence-only versions of the breakout/exit conditions, for marking entry/exit points on a chart without re-marking every day a trend stays valid), `get_mechanical_action(summary)` (deterministic 매수/HOLD/매도 from breakout/exit flags alone, no network — the sole source of truth for the action, see Core signal & sizing logic below), `get_ichimoku_confluence(summary, action)` (v3.16 — advisory-only: whether today's Ichimoku cloud position agrees with the mechanical action; never changes `action` or position sizing, only feeds a narrative sentence via `recommendation_engine`), and `scan_for_signals` which ranks a `{ticker: df}` map by breakout+volume-surge priority (documented future feature, not yet wired into the UI).
- `news_fetcher.py` — `fetch_ticker_news_exa(ticker, ...)` is the only source (the yfinance-based `fetch_ticker_news`/`fetch_news_for_tickers` were fully superseded by this and deleted in v2.8, not kept as unused parallel code). Queries Exa's search API (`https://api.exa.ai/search`, `x-api-key` header from `config.EXA_API_KEY`) with `category: "news"`, a `"{ticker} stock news"` query, and `startPublishedDate` from `config.EXA_NEWS_LOOKBACK_DAYS` (default 7); requests `contents.summary`. Maps Exa's `author` field to `publisher`, falling back to the article URL's domain (`urlparse(link).netloc`) if missing. Raises `ValueError` if `EXA_API_KEY` isn't set. `archive_news(drive_db, ticker, news_items, date=None)`: persists news to a per-calendar-date Drive JSON file (`_news_{date}.json`, `{ticker: [news_item, ...]}`), deduped by article link (falls back to title) so re-running on the same day doesn't store duplicates. `get_cached_news(drive_db, ticker, date=None)` (v3.11): read-through check against that same archive — returns the cached list if present, else `None`, so callers only hit Exa on a cache miss (shared across concurrent Streamlit users and cron re-runs on the same day).
- `openrouter_briefing.py` — calls OpenRouter's OpenAI-compatible `/chat/completions` endpoint directly via `requests` (no SDK dependency, shared `_call_chat` helper). `generate_briefing`: the "Mr. Serenity" noise-vs-signal news summary (not currently wired into the UI, but a distinct documented capability — not dead code). `generate_recommendation`: given news + a `signal_engine.get_latest_signal_summary` dict, returns `{"action": "매수"|"HOLD"|"매도", "text": ...}` — the LLM's own read of the situation, parsed from a required `추천: ...` first line (regex `_RECOMMENDATION_PATTERN`; defaults to `"HOLD"` if the model doesn't follow the format). **This action is advisory only** — `recommendation_engine` logs a warning if it disagrees with the mechanical action but always uses the mechanical one. `generate_portfolio_overview(results)` (v3.0): one-paragraph cross-asset synthesis across all of that day's `ASSET_CLASS_TICKERS` results, used by `report_builder.py` — commentary only, same advisory-only principle as `generate_recommendation` (never changes any individual mechanical action). `generate_recommendation` also accepts an optional `ichimoku_confluence` dict (v3.16, `signal_engine.get_ichimoku_confluence`) appended to the signal block sent to the LLM; `RECOMMENDATION_SYSTEM_PROMPT` explicitly instructs the model this is advisory-only context that must never change the mandatory `추천: ...` first line.
- `recommendation_engine.py` — shared recommendation logic used by both `app.py` (one ticker at a time, on user demand) and the cron (`recommend.yml` → `python recommendation_engine.py`, batch over `ASSET_CLASS_TICKERS`). `_is_data_fresh(raw_df)`: guards against generating a recommendation from stale data (last bar older than `config.DATA_FRESHNESS_MAX_AGE_DAYS`, default 4 days) — needed because `data_fetcher`'s per-ticker `try/except` means an overall-successful collection run can still have silently skipped individual tickers. `get_recommendation_for_ticker(drive_db, ticker, use_llm=True)`: computes the action via `signal_engine.get_mechanical_action` (always, no network); on HOLD, returns immediately with a fixed explanation and skips news/LLM entirely; on 매수/매도, fetches news (Exa — checking `news_fetcher.get_cached_news` first, v3.11, so a same-day repeat request for the same ticker doesn't re-hit Exa; using `ASSET_CLASS_TICKERS[ticker]["news_query"]` when set — see `data_fetcher.py` above — falling back to `"{ticker} stock news"` otherwise) + asks the LLM for a narrative, falling back to `_build_rule_based_explanation` (cites the exact numeric rule that fired) if either call fails — validated against a real OpenRouter 429 rate-limit response, the action is never dropped. `use_llm=False` (v3.11, app.py passes `config.STREAMLIT_ENABLE_LLM`) still collects news but skips the LLM call outright, going straight to the rule-based explanation — `_build_rule_based_explanation`'s `reason` param distinguishes this intentional skip ("비활성화") from an actual failure ("실패") in the generated text. On 매수/매도 (right after the HOLD-return), `signal_engine.get_ichimoku_confluence(summary, action)` (v3.16) is computed once and threaded through to whichever explanation path runs (`_build_rule_based_explanation`'s `ichimoku_confluence` param, or `openrouter_briefing.generate_recommendation`'s) — purely an advisory sentence about whether the Ichimoku cloud agrees with the action, never altering `action` or `suggested_shares`. If `config.SKIP_LLM_AND_NEWS` is set (v3.5, wired to `recommend.yml`'s `workflow_dispatch` input `skip_llm_and_news`, default `true`), it skips straight to the rule-based explanation without calling Exa/OpenRouter at all — for manually re-running the workflow to check the pipeline/report/Telegram plumbing without burning API quota; the scheduled `workflow_run` path never sets this. (`SKIP_LLM_AND_NEWS` and `use_llm=False` are independent: the former skips news too and is cron-only; the latter keeps news and is the Streamlit deployment toggle.) `SIGNAL_HISTORY_FILENAME = "_signal_history.json"` / `load_signal_history(drive_db)` / `backfill_signal_history(drive_db)` (v3.28, replacing v3.26's `load_recommendations`, now removed — it was a per-date read only ever used by the report-history table): a small `{date: {ticker: action}}` accumulator, one Drive read for the Streamlit report-history table's entire action-column grid instead of one `_recommendations_{date}.json` read per row (which also carries unused LLM text/news). `backfill_signal_history` rebuilds it from scratch from every existing `_recommendations_*.json` in Drive (via `DriveDB.list_filenames`, `_test`-suffixed dates skipped) — safe to re-run, always a full rebuild not an incremental append, but only covers the short window those files already exist for. `backfill_signal_history_from_prices(drive_db, tickers=None)` (v3.34) runs `signal_engine.compute_signals` + `get_mechanical_action` directly over each ticker's full stored OHLCV (`drive_db.load_ticker`) — pure computation, no network calls, but capped by whatever's in Drive's 5-year rolling snapshot. Bonus effect discovered when cross-checking it against the recommendations-based version: a couple of this session's manual weekend test runs had left stale entries in `_signal_history.json` dated on non-trading days (`_is_data_fresh`'s 4-day window doesn't check "is this a trading day," so a Saturday/Sunday run using Friday's still-fresh data got saved under that weekend's date) — the price-derived rebuild naturally excludes those since there's no OHLCV row for a day the market didn't open. `backfill_signal_history_deep(drive_db, start="2007-01-01", tickers=None)` (v3.36, deepest) skips Drive's OHLCV entirely and calls `data_fetcher.fetch_ohlcv(ticker, start=start)` directly (real yfinance calls, throttled via `config.YFINANCE_REQUEST_DELAY_SEC`, so this is a manual/occasional operation, not part of the daily cron) — Drive's per-ticker OHLCV storage is untouched, only the resulting accumulator is saved. `2007-01-01` covers 11/12 tickers fully; only BTC-USD (2014-09-17) is shorter regardless of start date since yfinance has nothing earlier for it (CPER, the previous straggler at 2011-11-15, was replaced by DBB — starts 2007-01-05 — in v3.38, closing that gap). Both deep-backfill functions share their per-ticker OHLCV→date-action conversion via `_signal_history_for_ticker(raw_df)` (v3.36, extracted to avoid duplicating that loop). Actually run against real data: 6,270 dates (2007-01-03 to today) — table build+styling for the Streamlit tab stayed under 200ms even at that size. `_recent_signal_history(history, days=30)` (v3.31): slices to the last N calendar days — used only for the daily report's embedded history table (see `report_builder.py`'s bullet below), not the Streamlit tab (which shows the unwindowed full history). `run_asset_class_recommendations(drive_db, tickers=None)`: batch entry point, persists results to `_recommendations_{date}.json`, updates `_signal_history.json` with that day's actions (skipped when `config.IS_TEST_REPORT` is set, same reasoning as the filename-suffix rule — test runs must never pollute persistent history), loads+windows `_recent_signal_history` for the report (v3.31), then (v3.0) builds+saves the combined daily report via `report_builder.build_daily_report_html`/`save_report` (wrapped in try/except — a failed report build never blocks the Telegram summary) and calls `telegram_notifier.notify_recommendations(results, report_url=...)` if Telegram env vars are set. Right before the report-build step, it also loads that day's open paper-trading positions (v3.21, `paper_trading.load_positions` + `compute_position_returns`, filtered to `status == "open"`, wrapped in its own try/except so a failure here can't drop the recommendation/report/Telegram results either) and passes them into both `build_daily_report_html(..., paper_positions=open_positions)` and `notify_recommendations(..., paper_positions=open_positions)` — this is a read-only call, `recommendation_engine`/the cron never opens or closes a paper-trading position itself. A single `file_date` (plain date, or `{date}_test` when `config.IS_TEST_REPORT` is set — v3.20, wired to `recommend.yml`'s `workflow_dispatch` input `is_test`, default `true`, independent of `skip_llm_and_news`) is used for **both** the recommendations JSON's filename **and** the report's filenames (Drive's `_report_{date}.html` and the local `docs/reports/{date}.html`, v3.22 — originally only the report was suffixed, which still let a manual test run silently overwrite that day's real recommendations archive) — so a manual sample/test publish can't overwrite either of that day's real artifacts; the scheduled `workflow_run` path never sets `is_test`, so production runs always keep the plain date filename for both. `report_url` is only set when `config.IS_TEST_REPORT` is falsy (v3.27) — a test publish's `report_builder.save_report` never writes `docs/reports/`, so a GitHub Pages URL for it would just 404; Telegram simply gets no report link on a test run. CLI entry point (`if __name__ == "__main__"`) is what `recommend.yml` runs.
- `chart_builder.py` — the shared Plotly figure builder (`build_ticker_chart_figure`) and `slice_to_period(signals, days)` (slices an already-`compute_signals()`'d DataFrame to a display window — callers compute signals on full history first so Donchian-100/ATR lookback isn't distorted, then slice only for display). Used by `app.py` and `report_builder.py`; both embed the figure as client-side-rendered interactive HTML/JS (`fig.to_html()` for the report, Streamlit's own Plotly renderer for the UI) — no server-side/headless image rendering anywhere in the pipeline (kaleido was removed in v3.0, see below), so `FONT_FAMILY = "Nanum Gothic, Malgun Gothic, Noto Sans CJK KR, ..."` is just a CSS font-stack hint for whichever browser renders it, not a CI dependency. Candle/volume/ATR subplot heights are `row_heights=[2/3, 1/6, 1/6]` (4:1:1 — briefly changed to 2:1:1 in v3.12, reverted to 3:1:1 in v3.13, readjusted to 4:1:1 in v3.17); legend trace names are abbreviated (`BB`, `DC20`, `손절선`, etc., v3.12) — report_builder.py's `.chart-legend-key` box spells these out since a standalone report page has no "소개" tab to fall back on the way the Streamlit UI does. Legend is horizontal, anchored below the chart (`legend=dict(orientation="h", y=-0.06, ...)`, v3.18 — a fixed-width vertical legend on the right squeezed the plot area too narrow on mobile). Only entries that actually need distinguishing are shown: 가격/거래량/ATR get `showlegend=False` (already self-evident from their own (sub)plot), and BB/DC20/DC100's upper+lower trace pairs share one `legendgroup` with only the representative trace visible (`legend.groupclick="togglegroup"` so clicking it toggles the whole pair) — 8 legend entries total as of v3.19 (BB, DC20, DC100, 손절선, 양운, 음운, 매수, 매도). BB's line/fill opacity was also lowered in v3.19 (`rgba(120,144,156,0.3)` line / `0.05` fill / `0.4` middle line, down from `0.6`/`0.12`/solid). Ichimoku overlay (v3.16, cloud-only as of v3.19): 전환선/기준선/후행스팬 are still computed in `signal_engine` (Senkou A needs Tenkan/Kijun) but are no longer plotted — only the cloud (Senkou A/B) is drawn, extended `config.ICHIMOKU_DISPLACEMENT` (26) business days past `view["Date"].max()` to match the traditional Ichimoku look (built by concatenating the already-displaced `Ichimoku_SenkouA`/`SenkouB` columns — historical portion — with the tail of the undisplaced `_Raw` columns re-anchored to `pd.bdate_range`-generated future dates — the future portion — continuous with no gap). `slice_to_period` itself is untouched — the future-date extension is built ad hoc inside `build_ticker_chart_figure`, not stored in any DataFrame. The cloud is colored per-segment (v3.19) — 양운 (bullish, Senkou A ≥ B) in light red (`rgba(239,83,80,...)`), 음운 (bearish) in light blue (`rgba(66,165,245,...)`) — since a single Plotly trace can't have a conditional fill color, the cloud is split into contiguous same-sign runs by the sign of (Senkou A − B) and each run gets its own filled trace pair (each segment includes its follow-up point too, so adjacent segments join with no visual gap); legend shows 양운/음운 once each via `legendgroup`+`showlegend` on only the first occurrence of each.
- `report_builder.py` (v3.0, extended v3.1) — builds the combined daily HTML report across all of `ASSET_CLASS_TICKERS`: `build_daily_report_html(drive_db, results)` assembles an LLM cross-asset overview (`openrouter_briefing.generate_portfolio_overview`, wrapped in try/except so a failed LLM call still yields a report with just the table+cards), an HTML summary table (grouped into category header rows — SPY/QQQ, then BTC-USD, etc. — since `results` already iterates `ASSET_CLASS_TICKERS` in definition order so same-category tickers are already contiguous, no sorting needed, v3.5; 매수/매도 ticker cells link down to their card via `#ticker-{ticker}` anchors), one `<section class="signal-card">` per 매수/매도 ticker (action badge, the LLM/rule-based analysis text and Exa news cards already computed by `recommendation_engine.get_recommendation_for_ticker` — reused as-is from `results[ticker]['text']`/`['news']`, no repeat Exa/LLM calls — plus its chart behind a collapsed `<details>`), and one collapsed `<details>` block at the end for HOLD tickers' charts only (no news/analysis exists for HOLD). Charts use `chart_builder.build_ticker_chart_figure` → `fig.to_html(include_plotlyjs="cdn")` for the first chart rendered anywhere on the page, `include_plotlyjs=False` for the rest (tracked via a shared `chart_js_loaded` mutable flag passed between the signal-card and HOLD builders) to avoid re-loading the CDN script per chart. All externally-sourced text (LLM output, Exa titles/summaries) is passed through `html.escape()` before insertion — see Implementation constraints. The page container has no `max-width` cap (`width: 97%` only, v3.4 — v3.3's `max-width: 1400px` still left excessive margins on wide monitors), so tables/charts/the news grid (`repeat(auto-fit, minmax(320px, 1fr))`) use nearly the full viewport width. The prose blocks (`.overview` cross-asset synthesis, `.analysis` per-ticker LLM/rule-based text) originally shared a `max-width: 900px` cap for readability — v3.30 dropped it from `.analysis` (per-ticker analysis felt narrow), and v3.33 dropped it from `.overview` too, for the same reason — both now use the full page width like everything else. News cards are a single vertical column (`display: flex; flex-direction: column`, v3.5 — an auto-fit multi-column grid tried in v3.3 made individual cards feel cramped) at a slightly smaller font (`0.88rem`, meta line `0.8rem`). ### Data flow

1. **`collect.yml`** (`cron: "57 21 * * 1-5"` — UTC Mon-Fri 21:57, which lands on KST Tue-Sat ~06:57 next day since UTC+9 crosses midnight — intentional, not a bug: a KST Monday-morning run would need a Sunday UTC trigger, but no new US trading day has happened yet at that point, so it'd just resend Friday's data. The minute is deliberately non-round (not :00/:15/:30/:45) since GitHub Actions queues scheduled workflows more heavily at those popular marks; scheduled runs are still best-effort regardless and have been observed firing up to ~1hr late. Moving the target earlier (from 22:30 UTC) to land closer to KST wake-up time trimmed the post-close buffer during EST (US winter) from ~1.5hr down to ~57min — accepted tradeoff, a missed same-day fetch just self-heals next run. `workflow_dispatch` also available) runs `data_fetcher.py update` (== `run_full_collection`) after market close.
2. `sync_universe` runs first: diffs the live S&P 500 list (Wikipedia's GICS Sector table, excluding `ASSET_CLASS_TICKERS` from the "stored" side of the diff — they're never S&P 500 constituents, so without the exclusion they'd get flagged as removed every run) against Drive's stored tickers. New entrants get backfilled via `run_initial_ingestion`; removed entrants keep their Parquet file (history preserved) but drop out of the active list. The result is written to `_universe.json` in the Drive folder (`{"active_tickers": [...], "inactive_tickers": [...], "sectors": {...}, "descriptions": {...}, "synced_at": ...}`) via `DriveDB.save_json`.
3. `run_daily_update` fetches only the tickers in `_universe.json`'s `active_tickers` (falling back to `DriveDB.list_tickers()` only if the universe file doesn't exist yet); `run_asset_class_update` does the same for the fixed asset-class set. Both use `_update_one_ticker`: new OHLCV rows are appended to each ticker's Parquet file via `DriveDB.upsert_ticker` (dedup by date, lookback anchored to that ticker's own last stored date — not a fixed "last N days from today" — so it self-heals if a run is skipped).
4. **`recommend.yml`** runs next, chained via `workflow_run` (only if `collect.yml` succeeded) or manually via `workflow_dispatch`. Runs `recommendation_engine.py`, which for each of `ASSET_CLASS_TICKERS` (not the full S&P 500): checks `_is_data_fresh` (skip if stale), computes signals + `signal_engine.get_mechanical_action` (deterministic action, no network), skips news/LLM entirely on HOLD, and on 매수/매도 fetches Exa news + asks the LLM for a narrative (falling back to `_build_rule_based_explanation` on failure). Results are saved to `_recommendations_{date}.json`.
5. (v3.0) `report_builder.build_daily_report_html` turns that day's results into one HTML page (LLM cross-asset overview + summary table + every ticker's chart), saved to Drive (`_report_{date}.html`) and to `docs/reports/{date}.html`; `recommend.yml`'s next step (`permissions: contents: write`) commits+pushes that file so GitHub Pages (serving `docs/`) publishes it at `https://garam827.github.io/ai_invest_assistant/reports/{date}.html`. A report build/save failure is caught and logged — it never blocks the Telegram summary below.
6. `telegram_notifier.notify_recommendations(results, report_url=...)` sends one message: the compact summary table (all tickers) plus a link to that report page. No chart images are attached directly anymore (v3.0 — they used to be, per-매수/매도-ticker, via kaleido; see the spec changelog for why that was removed).
7. In the Streamlit chart tabs (interactive, on-demand, one ticker at a time — no Telegram), `render_ticker_chart` calls `get_recommendation` → `recommendation_engine.get_recommendation_for_ticker`, the same function the cron uses, cached by `(ticker, latest_date)`. The "리포트 히스토리" tab separately reads past `_report_{date}.html` files straight from Drive.
8. Any new tab/feature should source its ticker universe from `_universe.json`'s `active_tickers`/`sectors`/`descriptions`, not a raw `DriveDB.list_tickers()`, so delisted/removed tickers don't show up in signal results (see the "종목 차트" tab for the established pattern).

### Core signal & sizing logic (must match spec exactly)

- **Donchian Channel**: dual window, 20-day and 100-day highs/lows, computed excluding today (`shift(1)`) so a breakout is measurable.
  - Buy signal: close breaks above the N-day high.
  - Exit signal: close breaks below the trailing stop line.
- **ATR**: 14-day Wilder's smoothing (`ewm(alpha=1/window, adjust=False)` in `signal_engine.calculate_atr`).
- **Bollinger Bands**: 20-day SMA ± 2 std dev — reference-only overlay, not part of the entry/exit rules.
- **Ichimoku Kinko Hyo** (v3.16): Tenkan/Kijun/Senkou A·B/Chikou — reference-only overlay, same as Bollinger Bands, never part of the entry/exit rules or position sizing. `signal_engine.get_ichimoku_confluence` only checks whether today's cloud position agrees with the mechanical action, feeding one advisory sentence into the recommendation narrative (`recommendation_engine`/`openrouter_briefing`) — it must never change `get_mechanical_action`'s output or `calculate_position_size`'s result (see rule 14 in the spec's 주의사항).
- **Trailing stop**: `highest_high_over_window - 3 * ATR`.
- **Position sizing**: `shares = (account_equity * risk_pct) // (3 * ATR)`, risk_pct defaults to 1% (`config.DEFAULT_RISK_PCT`).
- **False-breakout filter**: `Volume_Surge` (today's volume ≥ 1.5x the 20-day average, `config.VOLUME_SURGE_MULTIPLIER`) is purely a confidence/priority signal, never a gate — `get_mechanical_action` doesn't read it at all, so a low-volume breakout still fires 매수 exactly the same as a high-volume one. It only (a) highlights that day's bar on the volume subplot and (b) ranks candidates in `scan_for_signals` (not yet wired into the UI). Clarified in the app's 소개 tab glossary in v3.30 — "필터" in older wording shouldn't be read as "suppresses the action."
- **Asset-class trend following**: the same rules apply unmodified to `ASSET_CLASS_TICKERS` — raw indices (e.g. `^GSPC`) or yield quotes (e.g. `^TNX`) aren't directly tradable and often lack reliable volume data, hence tradable ETF/spot proxies (SPY for the S&P 500 itself, QQQ for the Nasdaq-100, BTC-USD for bitcoin, GLD for gold, TLT/IEF for long/mid-term Treasuries, DBC/USO/UNG/DBA/DBB for broad/oil/nat-gas/agriculture/base-metals commodities, UUP for the US Dollar Index, v3.20).
- **Mechanical action decoupling**: the 매수/HOLD/매도 call is always `signal_engine.get_mechanical_action(summary)` — pure rules, no network. The LLM (`openrouter_briefing.generate_recommendation`) only adds narrative on 매수/매도 days and is advisory-only; `recommendation_engine.get_recommendation_for_ticker` ignores the LLM's own action if it disagrees, and falls back to `_build_rule_based_explanation` if the LLM/news call fails outright, so the action is never lost or downgraded to HOLD by a network failure.

## Implementation constraints from the spec

- Throttle yfinance calls with `config.YFINANCE_REQUEST_DELAY_SEC` (default 0.5s) between tickers to avoid rate-limit blocks — already applied in `data_fetcher.py`'s loops.
- Avoid re-downloading full Parquet files from Google Drive on every read for frequently-accessed data — use Streamlit's `st.cache_data` (see `app.py`).
- The "Mr. Serenity" prompts (`openrouter_briefing.SYSTEM_PROMPT`, `RECOMMENDATION_SYSTEM_PROMPT`) must strip short-term noise/sentiment from news and judge only whether it reinforces or is irrelevant to the long-term trend / mechanical signal state — do not reword these casually, they're copied verbatim from the spec.
- Never let `sync_universe`'s S&P 500 membership diff include `data_fetcher.ASSET_CLASS_TICKERS` — they must stay excluded from the "stored" side of the diff or they'll be misclassified as delisted every run.
- Keep LLM calls behind a cache keyed on data freshness (e.g. `(ticker, latest_date)`), not just a short TTL — `st.tabs` executes every tab body on every rerun, so an uncached or short-TTL LLM call gets hit far more often than the user's actual clicks would suggest.
- The recommendation flow requires `EXA_API_KEY` (news) in addition to `OPENROUTER_API_KEY` (LLM) — both raise a clear `ValueError` if unset, don't silently fall back.
- Never let a news/LLM failure drop or downgrade the mechanical 매수/매도 action — fall back to a rule-based explanation (`recommendation_engine._build_rule_based_explanation`) instead.
- Don't reintroduce server-side/headless chart image rendering (kaleido etc.) without good reason — v3.0 removed it specifically to stop paying the "CJK font missing on a bare Ubuntu Actions runner" tax; charts are embedded as client-rendered HTML/JS (`fig.to_html()`) instead, in both the Streamlit UI and `report_builder.py`'s report.
- Never let a report-build failure (`report_builder`, LLM/Drive/git push) block the Telegram summary or the recommendation results themselves — same "don't drop what already succeeded" principle as the per-ticker LLM fallback.
- `recommend.yml` needs `permissions: contents: write` to commit+push `docs/reports/{date}.html` for GitHub Pages — don't drop that if the workflow is refactored.
- Always `html.escape()` LLM output and Exa article title/summary text before inserting it into `report_builder.py`'s f-string-built HTML — it's external/untrusted text, and unescaped `<`/`>` would break the page's markup.
- Don't re-fetch news or re-call the LLM for data `recommendation_engine.get_recommendation_for_ticker` already computed — `results[ticker]['news']`/`['text']` should be reused as-is wherever they're displayed (report, Telegram, Streamlit).
- Local `.env` and GitHub Actions Secrets are two entirely separate stores — editing one does not touch the other. After changing a credential locally (e.g. switching `TELEGRAM_CHAT_ID` from a 1:1 chat to a group), also run `gh secret set <NAME>` or it silently keeps using the old value in the scheduled workflow. `gh secret list` shows each secret's last-updated timestamp, which is the fastest way to check whether it's actually in sync with a recent `.env` change.
- For a manual `recommend.yml` test run that shouldn't burn Exa/OpenRouter quota, use `gh workflow run recommend.yml -f skip_llm_and_news=true` (also the default when triggered from the Actions tab UI) — see `config.SKIP_LLM_AND_NEWS` above.
- Manual/sample `recommend.yml` runs also default `is_test=true` (`config.IS_TEST_REPORT`, v3.20-v3.22), which appends `_test` to the published report's filename (both Drive and `docs/reports/`) **and** the recommendations JSON's filename (`_recommendations_{date}.json`, v3.22) so a sample publish never overwrites that day's real report or recommendations archive — pass `-f is_test=false` only when intentionally publishing the real thing by hand (e.g. re-running after a failure).
- Never call `paper_trading.open_position`/`close_position` from `collect.yml`/`recommend.yml` or any other cron path — those are the two mutation points the "모의 투자" feature deliberately restricts to the Streamlit UI (v3.21); the cron only ever reads positions (`load_positions`/`compute_position_returns`) to include in the report/Telegram summary.

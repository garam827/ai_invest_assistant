The Streamlit UI ([기능 4]) is a single page (`app.py`, no top-level `st.title` — deliberately removed) split into six `st.tabs`: **소개** (about-the-program / Tom Basso philosophy blurb + the indicator glossary table — no analysis functionality, purely reference), **대표 자산군 분석** (asset-class trend analysis across 12 tickers in 6 categories — see Architecture below), **종목 차트 (S&P 500)** (per-ticker candlestick + signal chart), **데이터 적재** (the manual data-collection trigger — originally tab 1, moved as more tabs were added), **리포트 히스토리** (browse past daily reports stored in Drive, added in v3.0), and **모의 투자** (manual paper-trading positions + live P&L, added in v3.21 — see `paper_trading.py`). Deliberately a single page, not a multipage `pages/` app (removed by request). The all-tickers signal scan table and the chat tab are not built.

**Automation is live** ([기능 5]): GitHub Actions (`.github/workflows/collect.yml` + `recommend.yml`, chained via `workflow_run`) replaced the originally-planned GCP Cloud Run/Cloud Scheduler (abandoned over billing-account friction). `collect.yml` runs `python data_fetcher.py update` on a weekday cron; on success, `recommend.yml` runs `python recommendation_engine.py`, which generates 매수/HOLD/매도 calls for `ASSET_CLASS_TICKERS` only (not all 503 S&P 500 tickers — keeps LLM/news usage bounded), builds a combined daily HTML report (`report_builder.py`) that it commits to `docs/reports/{date}.html` for GitHub Pages to serve publicly, and sends a Telegram summary + report link. The "데이터 적재" tab's button remains as a manual, on-demand alternative to the collect cron. There is no test suite or lint config yet — when one is added, update this file with the actual commands.

Setup: `pip install -r requirements.txt`, copy `.env.example` to `.env` and fill in `DRIVE_FOLDER_ID` / `GOOGLE_OAUTH_CLIENT_SECRET_PATH` / `OPENROUTER_API_KEY` / `EXA_API_KEY` (see [GOOGLE_DRIVE_SETUP.md](GOOGLE_DRIVE_SETUP.md) for the Drive OAuth setup) and optionally `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` (see [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md) — daily recommendation notifications, cron-only). `data_fetcher.py` is runnable directly: `python data_fetcher.py init` (5y backfill of S&P 500 + asset-class tickers, run once), `python data_fetcher.py update` (S&P 500 membership sync + daily append + asset-class update, the intended cron command — same as `data_fetcher.run_full_collection`), or `python data_fetcher.py sync` (S&P 500 membership reconciliation only). All 503 current S&P 500 tickers plus all `ASSET_CLASS_TICKERS` have already been backfilled into the live Drive folder. Run the UI with `streamlit run app.py`. To deploy the UI publicly, see [GCP_Setyo_Guide.md](GCP_Setyo_Guide.md) (GCP Compute Engine + Docker Compose — the adopted path, v3.15; `docker-compose.yml`/`Dockerfile`/`.dockerignore` already in the repo root). ## What this project is

A Tom Basso-style ("Mr. Serenity") trend-following investment assistant chatbot: a rule-based, ATR-driven trend-following signal and position-sizing engine wrapped in an LLM chat interface, applied to both individual S&P 500 stocks and representative asset-class proxies (equities, crypto, precious metals, bonds, commodities). Full spec (versioned, latest first): [investment_assistant_spec.md](investment_assistant_spec.md).

## Architecture

- **Frontend / Chat UI**: Streamlit, single page (`app.py`) with `st.tabs` separating features (not a multipage `pages/` app — everything runs in one process/session so tabs share `st.cache_resource`/`st.cache_data` state directly)
- **Data source**: yfinance (Yahoo Finance API) — daily OHLCV for all S&P 500 tickers plus `data_fetcher.ASSET_CLASS_TICKERS` (12 tickers across 6 categories: 주식 `SPY`/`QQQ`, 암호화폐 `BTC-USD`, 귀금속 `GLD`, 채권 `TLT`/`IEF`, 원자재 `DBC`/`USO`/`UNG`/`DBA`/`DBB`, 통화 `UUP`). News for the LLM recommendation flow comes from the **Exa search API** (`news_fetcher.fetch_ticker_news_exa`), not yfinance — see below.
- **"Database"**: Google Drive API storing one Apache Parquet file per ticker (`[Ticker].parquet`), accessed via OAuth user credentials (not a service account — the GCP project enforces `iam.disableServiceAccountKeyCreation`, see [GOOGLE_DRIVE_SETUP.md](GOOGLE_DRIVE_SETUP.md)) — see `drive_db.DriveDB`. Also stores small JSON metadata files: `_universe.json` (S&P 500 active/inactive tickers + sectors + descriptions), `_news_{YYYY-MM-DD}.json` (per-date news archive, see below), and `_recommendations_{YYYY-MM-DD}.json` (daily cron recommendation results).
- **LLM engine**: OpenRouter (default model `nvidia/nemotron-3-ultra-550b-a55b:free`, configurable via `OPENROUTER_MODEL_NAME`) — see `openrouter_briefing.py`. Switched from Vertex AI/Gemini for cost reasons (see spec changelog). The buy/hold/sell **action** itself never depends on the LLM (see Core signal & sizing logic below) — the LLM only adds narrative explanation on 매수/매도 days.
- **Infra**: GitHub Actions (`.github/workflows/collect.yml` + `recommend.yml`, chained via `workflow_run`) — see Data flow below. Originally planned as GCP Cloud Run + Cloud Scheduler, abandoned over a billing-account blocker.
- **Report hosting**: GitHub Pages, serving the repo's `docs/` folder (`https://garam827.github.io/ai_invest_assistant/`) — `recommend.yml` commits the day's `report_builder.py`-generated HTML into `docs/reports/{date}.html`. No separate hosting account/billing needed since it's the same repo already used for GitHub Actions.
- **Notifications**: Telegram (`telegram_notifier.py`), cron-only — see [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

### Module map

- `config.py` — all tunables/secrets, loaded from `.env`. Every other module reads from here rather than hardcoding constants.
- `drive_db.py` — `DriveDB` class: Drive OAuth user auth (browser consent on first run, cached to `token.json` thereafter), per-ticker Parquet find/download/upload, `upsert_ticker` (concat + `drop_duplicates` by Date + re-upload), generic `load_json`/`save_json` for small metadata files (used for the ticker universe and the news archive, see below), `load_text`/`save_text` (v3.0, same pattern for the HTML daily report), and `list_filenames(prefix)` (v3.0, lists Drive filenames starting with a prefix — used to enumerate saved report dates).
- `data_fetcher.py` — S&P 500 ticker list (scraped from Wikipedia via `requests` + a browser User-Agent, since Wikipedia 403s the default urllib UA — parsed with `pd.read_html(io.StringIO(...))`), yfinance OHLCV fetch, `run_initial_ingestion` (5y backfill), `sync_universe` (reconciles S&P 500 membership changes, see Data flow below), `run_daily_update` (delta fetch + upsert for the active S&P 500 universe), `run_asset_class_update` (same delta-fetch logic, applied to the fixed `ASSET_CLASS_TICKERS` dict — independent of S&P membership), `run_full_collection` (all three, in order — what the "데이터 적재" tab and `python data_fetcher.py update` both run). `_update_one_ticker` is the shared per-ticker delta-fetch-and-upsert helper both `run_daily_update` and `run_asset_class_update` call. `ASSET_CLASS_TICKERS` is `{ticker: {"label": display_name, "category": category, "description": one_liner, "news_query": macro_query}}` — categories: 주식/암호화폐/귀금속/채권/원자재/통화 (`UUP`, v3.20). `news_query` (v3.3) is an English macro-oriented search phrase used instead of the ticker for Exa news lookups — `"GLD stock news"` mostly surfaces "GLD down X%" wire blurbs, not the macro drivers behind the move, so proxies search under the underlying asset's name instead (e.g. `"gold price outlook macro drivers analysis"` for GLD). `sync_universe` also builds a `{ticker: "회사명 (GICS 세부업종)"}` description map from the same Wikipedia table (no extra requests) and writes it into `_universe.json`'s `descriptions` key for all active S&P 500 tickers. CLI entry point via `if __name__ == "__main__"` with `init`/`update`/`sync` modes. **`MACRO_TICKERS`/`fetch_macro_snapshot` (v3.56, user request for a report-level macro-context strip)**: deliberately separate from `ASSET_CLASS_TICKERS` — these are raw index/yield quotes (VIX `^VIX`; short/mid/long US Treasury yields `^IRX` 13주/`^TNX` 10년/`^TYX` 30년), never stored to Drive, never run through `signal_engine`, no trend-following signal of their own, pure display. `fetch_macro_snapshot()` pulls all of these live via yfinance at report-build time (not cached); a per-ticker failure is skipped, not fatal, same pattern as everywhere else in this pipeline. yfinance's `^IRX`/`^TNX`/`^TYX` closes are already yields in percent (e.g. `4.736` == 4.736%), not the historical CBOE "yield×10" convention — verified directly, no scaling needed. A High Yield bond spread entry (FRED series `BAMLH0A0HYM2`) was tried and then dropped entirely (v3.57, user request) — FRED's unauthenticated CSV export dropped the connection outright on most attempts (confirmed structural, not transient: even 5 retries with backoff all failed, both locally and in a real `recommend.yml` run), and switching to FRED's official API (which worked reliably) would have required the user to provision a new API key — not worth the setup cost for one metric, so it was cancelled outright rather than shipped either way.
- `signal_engine.py` — pure pandas, no I/O, and ticker-agnostic (same functions work on S&P stocks or asset-class tickers). Donchian channel, Wilder ATR, Bollinger Bands (reference-only, not part of the entry/exit rules), Ichimoku Kinko Hyo (`calculate_ichimoku`, v3.16 — Tenkan/Kijun/displaced Senkou A·B/Chikou, plus undisplaced `_Raw` Senkou columns consumed only by `chart_builder.py` for the future cloud tip; reference-only, same as BB), trailing stop, volume-surge filter, position sizing, `Buy_Trigger`/`Sell_Trigger` (first-occurrence-only versions of the breakout/exit conditions, for marking entry/exit points on a chart without re-marking every day a trend stays valid), `get_mechanical_action(summary)` (deterministic 매수/HOLD/매도 from breakout/exit flags alone, no network — the sole source of truth for the action, see Core signal & sizing logic below), `get_ichimoku_confluence(summary, action)` (v3.16 — advisory-only: whether today's Ichimoku cloud position agrees with the mechanical action; never changes `action` or position sizing, only feeds a narrative sentence via `recommendation_engine`), and `scan_for_signals` which ranks a `{ticker: df}` map by breakout+volume-surge priority (documented future feature, not yet wired into the UI).
- `news_fetcher.py` — `fetch_ticker_news_exa(ticker, ...)` is the only source (the yfinance-based `fetch_ticker_news`/`fetch_news_for_tickers` were fully superseded by this and deleted in v2.8, not kept as unused parallel code). Queries Exa's search API (`https://api.exa.ai/search`, `x-api-key` header from `config.EXA_API_KEY`) with `category: "news"`, a `"{ticker} stock news"` query, and `startPublishedDate` from `config.EXA_NEWS_LOOKBACK_DAYS` (default 7); requests `contents.summary`. Maps Exa's `author` field to `publisher`, falling back to the article URL's domain (`urlparse(link).netloc`) if missing. Raises `ValueError` if `EXA_API_KEY` isn't set. `archive_news(drive_db, ticker, news_items, date=None)`: persists news to a per-calendar-date Drive JSON file (`_news_{date}.json`, `{ticker: [news_item, ...]}`), deduped by article link (falls back to title) so re-running on the same day doesn't store duplicates. `get_cached_news(drive_db, ticker, date=None)` (v3.11): read-through check against that same archive — returns the cached list if present, else `None`, so callers only hit Exa on a cache miss (shared across concurrent Streamlit users and cron re-runs on the same day). **`MACRO_NEWS_ARCHIVE_KEY`/`MACRO_NEWS_QUERY` (v3.59, user request for a report-level "오늘 챙겨야 할 해외 이슈" digest)**: not a new fetch function — `recommendation_engine.get_macro_issues_briefing` calls the same `fetch_ticker_news_exa` with `MACRO_NEWS_ARCHIVE_KEY` (`"_MACRO_ISSUES_"`, a fixed pseudo-ticker string, not a real ticker) as the `ticker` arg and `MACRO_NEWS_QUERY` (a general English macro/geopolitical search phrase, not tied to any single asset) as an explicit `query` override, so the existing per-date `archive_news`/`get_cached_news` cache mechanism just works under this key with zero new code in this module. Uses `config.MACRO_NEWS_MAX_ITEMS`/`MACRO_NEWS_LOOKBACK_DAYS` (defaults 8 items / 2 days — deliberately shorter than `EXA_NEWS_LOOKBACK_DAYS`'s 7-day default, since this section is meant to surface what's fresh today, not a week-old backlog).
- `openrouter_briefing.py` — calls OpenRouter's OpenAI-compatible `/chat/completions` endpoint directly via `requests` (no SDK dependency, shared `_call_chat` helper). `generate_briefing`: the "Mr. Serenity" noise-vs-signal news summary (not currently wired into the UI, but a distinct documented capability — not dead code). `generate_recommendation`: given news + a `signal_engine.get_latest_signal_summary` dict, returns `{"action": "매수"|"HOLD"|"매도", "text": ...}` — the LLM's own read of the situation, parsed from a required `추천: ...` first line (regex `_RECOMMENDATION_PATTERN`; defaults to `"HOLD"` if the model doesn't follow the format). **This action is advisory only** — `recommendation_engine` logs a warning if it disagrees with the mechanical action but always uses the mechanical one. `generate_portfolio_overview(results, signal_history=None)` (v3.0, `signal_history` param added v3.40): one-paragraph cross-asset synthesis across all of that day's `ASSET_CLASS_TICKERS` results, used by `report_builder.py` — commentary only, same advisory-only principle as `generate_recommendation` (never changes any individual mechanical action). When `signal_history` (v3.40, the same `{date: {ticker: action}}` dict `report_builder.build_daily_report_html` already receives — see its bullet below) is given and non-empty, its dated ticker/action lines are appended to the same prompt so the synthesis can also note trend shifts/synchronization across the recent window, not just today's snapshot — no extra LLM call, just more context on the existing one. `PORTFOLIO_OVERVIEW_SYSTEM_PROMPT` was extended accordingly (still forbids altering/reinterpreting any mechanical action or adding forward-looking predictions). `generate_recommendation` also accepts an optional `ichimoku_confluence` dict (v3.16, `signal_engine.get_ichimoku_confluence`) appended to the signal block sent to the LLM; `RECOMMENDATION_SYSTEM_PROMPT` explicitly instructs the model this is advisory-only context that must never change the mandatory `추천: ...` first line. **v3.46, two quality fixes found by reviewing a real published report**: (1) `RECOMMENDATION_SYSTEM_PROMPT` now explicitly asks the model to substantively engage with the 1-2 most relevant collected news articles (what they actually say, why it's fact vs. noise) instead of just naming topic keywords — the prior wording only said "filter whether news is fact-based," which produced a single compressed clause rather than real engagement with article content. (2) `generate_prediction_commentary`'s numeric comparison moved out of the LLM's hands entirely — a real run had the model claim QQQ/SPY were "above their historical average" when both were actually below it (mis-comparing two signed floats across 12 tickers in one pass), so the "above/below average" label per ticker is now precomputed in Python and handed to the model pre-labeled in the prompt (`PREDICTION_COMMENTARY_SYSTEM_PROMPT` also now says to trust that label rather than recompute it) — verified this fixes the exact case that failed (correctly grouped QQQ/SPY into "below average" alongside the bond tickers on rerun). **v3.55** (user feedback: the report's cross-asset overview read as a flat re-listing of that day's per-ticker actions, not an actual synthesis): `PORTFOLIO_OVERVIEW_SYSTEM_PROMPT` explicitly bans restating the table and now directs the model at three specific angles instead — (1) whether risk-on tickers (주식/암호화폐) and safe-haven/hedge tickers (채권/통화/귀금속/원자재) are moving together or diverging and what that implies about risk appetite, (2) whether the recent-history window (when given) is reinforcing or reversing today's snapshot, (3) whether any one asset class is breaking from the rest and why that's worth flagging — same "advisory-only, never re-scores the mechanical action" and rule-17-scoped "no price/direction forecasting, no definitive phrasing" constraints as before, just aimed at explaining what the combination means rather than only stating that it happened. `generate_portfolio_overview` also now labels each ticker line with its `data_fetcher.ASSET_CLASS_TICKERS` category (new module-level `import data_fetcher`, no circular import since `data_fetcher` doesn't import this module) so the model has the risk-on/safe-haven grouping handed to it directly rather than needing to infer it from ticker symbols alone. **`generate_macro_issues_briefing(news_items)` (v3.59, user request: "레포트에 투자와 연관 있어서 꼭 챙겨야 하는 국내외 이슈 정리")**: distills a batch of general (non-ticker-specific) 해외 매크로/지정학 news (from `news_fetcher`'s `MACRO_NEWS_QUERY` search, fed in by `recommendation_engine.get_macro_issues_briefing`) into a short numbered list — user chose the "해외(미국/글로벌) 위주" scope over adding Korean-domestic coverage, since the project has no Korean market data/tickers to anchor domestic issues to. `MACRO_ISSUES_SYSTEM_PROMPT` asks for 3-5 issues, each explained (not just keyword-listed) from the actual article content, under the same advisory-only/no-price-forecasting/no-definitive-phrasing constraints as `PORTFOLIO_OVERVIEW_SYSTEM_PROMPT` — this summary never changes any ticker's mechanical action. Reuses `_format_news_for_prompt` (unmodified) rather than a new formatter. Verified against a real test publish (`gh workflow run recommend.yml -f is_test=true -f skip_llm_and_news=false`, 2026-08-23): real Exa results + a real OpenRouter call produced a substantive 5-issue breakdown (Treasury term-premium/Fed policy, breakeven inflation, Fed communication opacity, PMI/inflation crosscurrents, Middle East geopolitical risk), but the model defaulted to Markdown syntax (`**bold**`, `### headers`, `---`, bullet lists) — since this section (like `overview`/per-ticker `analysis`) is inserted as plain escaped text, not rendered Markdown, that showed up as literal asterisks/hashes in the report. `MACRO_ISSUES_SYSTEM_PROMPT` now explicitly forbids Markdown syntax and asks for plain prose (numbers + line breaks only), matching the rest of the report's plain-paragraph style.
- `recommendation_engine.py` — shared recommendation logic used by both `app.py` (one ticker at a time, on user demand) and the cron (`recommend.yml` → `python recommendation_engine.py`, batch over `ASSET_CLASS_TICKERS`). `_is_data_fresh(raw_df)`: guards against generating a recommendation from stale data (last bar older than `config.DATA_FRESHNESS_MAX_AGE_DAYS`, default 4 days) — needed because `data_fetcher`'s per-ticker `try/except` means an overall-successful collection run can still have silently skipped individual tickers. `get_recommendation_for_ticker(drive_db, ticker, use_llm=True)`: computes the action via `signal_engine.get_mechanical_action` (always, no network); on HOLD, returns immediately with a fixed explanation and skips news/LLM entirely; on 매수/매도, fetches news (Exa — checking `news_fetcher.get_cached_news` first, v3.11, so a same-day repeat request for the same ticker doesn't re-hit Exa; using `ASSET_CLASS_TICKERS[ticker]["news_query"]` when set — see `data_fetcher.py` above — falling back to `"{ticker} stock news"` otherwise) + asks the LLM for a narrative, falling back to `_build_rule_based_explanation` (cites the exact numeric rule that fired) if either call fails — validated against a real OpenRouter 429 rate-limit response, the action is never dropped. `use_llm=False` (v3.11, app.py passes `config.STREAMLIT_ENABLE_LLM`) still collects news but skips the LLM call outright, going straight to the rule-based explanation — `_build_rule_based_explanation`'s `reason` param distinguishes this intentional skip ("비활성화") from an actual failure ("실패") in the generated text. On 매수/매도 (right after the HOLD-return), `signal_engine.get_ichimoku_confluence(summary, action)` (v3.16) is computed once and threaded through to whichever explanation path runs (`_build_rule_based_explanation`'s `ichimoku_confluence` param, or `openrouter_briefing.generate_recommendation`'s) — purely an advisory sentence about whether the Ichimoku cloud agrees with the action, never altering `action` or `suggested_shares`. If `config.SKIP_LLM_AND_NEWS` is set (v3.5, wired to `recommend.yml`'s `workflow_dispatch` input `skip_llm_and_news`, default `true`), it skips straight to the rule-based explanation without calling Exa/OpenRouter at all — for manually re-running the workflow to check the pipeline/report/Telegram plumbing without burning API quota; the scheduled `workflow_run` path never sets this. (`SKIP_LLM_AND_NEWS` and `use_llm=False` are independent: the former skips news too and is cron-only; the latter keeps news and is the Streamlit deployment toggle.) `SIGNAL_HISTORY_FILENAME = "_signal_history.json"` / `load_signal_history(drive_db)` / `backfill_signal_history(drive_db)` (v3.28, replacing v3.26's `load_recommendations`, now removed — it was a per-date read only ever used by the report-history table): a small `{date: {ticker: action}}` accumulator, one Drive read for the Streamlit report-history table's entire action-column grid instead of one `_recommendations_{date}.json` read per row (which also carries unused LLM text/news). `backfill_signal_history` rebuilds it from scratch from every existing `_recommendations_*.json` in Drive (via `DriveDB.list_filenames`, `_test`-suffixed dates skipped) — safe to re-run, always a full rebuild not an incremental append, but only covers the short window those files already exist for. `backfill_signal_history_from_prices(drive_db, tickers=None)` (v3.34) runs `signal_engine.compute_signals` + `get_mechanical_action` directly over each ticker's full stored OHLCV (`drive_db.load_ticker`) — pure computation, no network calls, but capped by whatever's in Drive's 5-year rolling snapshot. Bonus effect discovered when cross-checking it against the recommendations-based version: a couple of this session's manual weekend test runs had left stale entries in `_signal_history.json` dated on non-trading days (`_is_data_fresh`'s 4-day window doesn't check "is this a trading day," so a Saturday/Sunday run using Friday's still-fresh data got saved under that weekend's date) — the price-derived rebuild naturally excludes those since there's no OHLCV row for a day the market didn't open. `backfill_signal_history_deep(drive_db, start="2007-01-01", tickers=None)` (v3.36, deepest) skips Drive's OHLCV entirely and calls `data_fetcher.fetch_ohlcv(ticker, start=start)` directly (real yfinance calls, throttled via `config.YFINANCE_REQUEST_DELAY_SEC`, so this is a manual/occasional operation, not part of the daily cron) — Drive's per-ticker OHLCV storage is untouched, only the resulting accumulator is saved. `2007-01-01` covers 11/12 tickers fully; only BTC-USD (2014-09-17) is shorter regardless of start date since yfinance has nothing earlier for it (CPER, the previous straggler at 2011-11-15, was replaced by DBB — starts 2007-01-05 — in v3.38, closing that gap). Both deep-backfill functions share their per-ticker OHLCV→date-action conversion via `_signal_history_for_ticker(raw_df)` (v3.36, extracted to avoid duplicating that loop). Actually run against real data: 6,270 dates (2007-01-03 to today) — table build+styling for the Streamlit tab stayed under 200ms even at that size. `_recent_signal_history(history, days=20)` (v3.31, weekday-only + default 20 since v3.44): slices to the most recent N *weekday* dates (`pd.Timestamp(date).dayofweek < 5` filters out weekends before counting) — used only for the daily report's embedded history table (see `report_builder.py`'s bullet below), not the Streamlit tab (which shows the unwindowed full history). Originally a 30-*calendar*-day cutoff; changed because `history`'s date axis includes BTC-USD's weekend entries, so a plain "last N recorded dates" wasted rows on weekend dates that are blank for the other 11 tickers — filtering to weekdays first keeps the report table a genuine N trading days. ### Data flow

1. **`collect.yml`** (`cron: "57 21 * * 1-5"` — UTC Mon-Fri 21:57, which lands on KST Tue-Sat ~06:57 next day since UTC+9 crosses midnight — intentional, not a bug: a KST Monday-morning run would need a Sunday UTC trigger, but no new US trading day has happened yet at that point, so it'd just resend Friday's data. The minute is deliberately non-round (not :00/:15/:30/:45) since GitHub Actions queues scheduled workflows more heavily at those popular marks; scheduled runs are still best-effort regardless and have been observed firing up to ~1hr late. Moving the target earlier (from 22:30 UTC) to land closer to KST wake-up time trimmed the post-close buffer during EST (US winter) from ~1.5hr down to ~57min — accepted tradeoff, a missed same-day fetch just self-heals next run. `workflow_dispatch` also available) runs `data_fetcher.py update` (== `run_full_collection`) after market close.
2. `sync_universe` runs first: diffs the live S&P 500 list (Wikipedia's GICS Sector table, excluding `ASSET_CLASS_TICKERS` from the "stored" side of the diff — they're never S&P 500 constituents, so without the exclusion they'd get flagged as removed every run) against Drive's stored tickers. New entrants get backfilled via `run_initial_ingestion`; removed entrants keep their Parquet file (history preserved) but drop out of the active list. The result is written to `_universe.json` in the Drive folder (`{"active_tickers": [...], "inactive_tickers": [...], "sectors": {...}, "descriptions": {...}, "synced_at": ...}`) via `DriveDB.save_json`.
3. `run_daily_update` fetches only the tickers in `_universe.json`'s `active_tickers` (falling back to `DriveDB.list_tickers()` only if the universe file doesn't exist yet); `run_asset_class_update` does the same for the fixed asset-class set. Both use `_update_one_ticker`: new OHLCV rows are appended to each ticker's Parquet file via `DriveDB.upsert_ticker` (dedup by date, lookback anchored to that ticker's own last stored date — not a fixed "last N days from today" — so it self-heals if a run is skipped).
4. **`recommend.yml`** runs next, chained via `workflow_run` (only if `collect.yml` succeeded) or manually via `workflow_dispatch`. Runs `recommendation_engine.py`, which for each of `ASSET_CLASS_TICKERS` (not the full S&P 500): checks `_is_data_fresh` (skip if stale), computes signals + `signal_engine.get_mechanical_action` (deterministic action, no network), skips news/LLM entirely on HOLD, and on 매수/매도 fetches Exa news + asks the LLM for a narrative (falling back to `_build_rule_based_explanation` on failure). Results are saved to `_recommendations_{date}.json`.
5. (v3.0) `report_builder.build_daily_report_html` turns that day's results into one HTML page (LLM cross-asset overview + summary table + every ticker's chart), saved to Drive (`_report_{date}.html`) and to `docs/reports/{date}.html`; `recommend.yml`'s next step (`permissions: contents: write`) commits+pushes that file so GitHub Pages (serving `docs/`) publishes it at `https://garam827.github.io/ai_invest_assistant/reports/{date}.html`. A report build/save failure is caught and logged — it never blocks the Telegram summary below.
6. `telegram_notifier.notify_recommendations(results, report_url=...)` sends one message: the compact summary table (all tickers) plus a link to that report page. No chart images are attached directly anymore (v3.0 — they used to be, per-매수/매도-ticker, via kaleido; see the spec changelog for why that was removed).
7. In the Streamlit chart tabs (interactive, on-demand, one ticker at a time — no Telegram), `render_ticker_chart` calls `get_recommendation` → `recommendation_engine.get_recommendation_for_ticker`, the same function the cron uses, cached by `(ticker, latest_date)`. The "리포트 히스토리" tab separately reads past `_report_{date}.html` files straight from Drive.
8. Any new tab/feature should source its ticker universe from `_universe.json`'s `active_tickers`/`sectors`/`descriptions`, not a raw `DriveDB.list_tickers()`, so delisted/removed tickers don't show up in signal results (see the "종목 차트" tab for the established pattern).

### Core signal & sizing logic (must match spec exactly)

- **Donchian Channel**: dual window, 20-day and 100-day highs/lows, computed excluding today (`shift(1)`) so a breakout is measurable.
  - Buy signal: close breaks above the N-day high.
  - Exit signal: close breaks below the trailing stop line.
- **ATR**: 14-day Wilder's smoothing (`ewm(alpha=1/window, adjust=False)` in `signal_engine.calculate_atr`).
- **Bollinger Bands**: 20-day SMA ± 2 std dev — reference-only overlay, not part of the entry/exit rules.
- **Ichimoku Kinko Hyo** (v3.16): Tenkan/Kijun/Senkou A·B/Chikou — reference-only overlay, same as Bollinger Bands, never part of the entry/exit rules or position sizing. `signal_engine.get_ichimoku_confluence` only checks whether today's cloud position agrees with the mechanical action, feeding one advisory sentence into the recommendation narrative (`recommendation_engine`/`openrouter_briefing`) — it must never change `get_mechanical_action`'s output or `calculate_position_size`'s result (see rule 14 in the spec's 주의사항).
- **Trailing stop**: `highest_high_over_window - 3 * ATR`.
- **Position sizing**: `shares = (account_equity * risk_pct) // (3 * ATR)`, risk_pct defaults to 1% (`config.DEFAULT_RISK_PCT`).
- **False-breakout filter**: `Volume_Surge` (today's volume ≥ 1.5x the 20-day average, `config.VOLUME_SURGE_MULTIPLIER`) is purely a confidence/priority signal, never a gate — `get_mechanical_action` doesn't read it at all, so a low-volume breakout still fires 매수 exactly the same as a high-volume one. It only (a) highlights that day's bar on the volume subplot and (b) ranks candidates in `scan_for_signals` (not yet wired into the UI). Clarified in the app's 소개 tab glossary in v3.30 — "필터" in older wording shouldn't be read as "suppresses the action."
- **Asset-class trend following**: the same rules apply unmodified to `ASSET_CLASS_TICKERS` — raw indices (e.g. `^GSPC`) or yield quotes (e.g. `^TNX`) aren't directly tradable and often lack reliable volume data, hence tradable ETF/spot proxies (SPY for the S&P 500 itself, QQQ for the Nasdaq-100, BTC-USD for bitcoin, GLD for gold, TLT/IEF for long/mid-term Treasuries, DBC/USO/UNG/DBA/DBB for broad/oil/nat-gas/agriculture/base-metals commodities, UUP for the US Dollar Index, v3.20).
- **Mechanical action decoupling**: the 매수/HOLD/매도 call is always `signal_engine.get_mechanical_action(summary)` — pure rules, no network. The LLM (`openrouter_briefing.generate_recommendation`) only adds narrative on 매수/매도 days and is advisory-only; `recommendation_engine.get_recommendation_for_ticker` ignores the LLM's own action if it disagrees, and falls back to `_build_rule_based_explanation` if the LLM/news call fails outright, so the action is never lost or downgraded to HOLD by a network failure.

## Implementation constraints from the spec

- Throttle yfinance calls with `config.YFINANCE_REQUEST_DELAY_SEC` (default 0.5s) between tickers to avoid rate-limit blocks — already applied in `data_fetcher.py`'s loops.
- Avoid re-downloading full Parquet files from Google Drive on every read for frequently-accessed data — use Streamlit's `st.cache_data` (see `app.py`).
- The "Mr. Serenity" prompts (`openrouter_briefing.SYSTEM_PROMPT`, `RECOMMENDATION_SYSTEM_PROMPT`) must strip short-term noise/sentiment from news and judge only whether it reinforces or is irrelevant to the long-term trend / mechanical signal state — do not reword these casually, they're copied verbatim from the spec.
- Never let `sync_universe`'s S&P 500 membership diff include `data_fetcher.ASSET_CLASS_TICKERS` — they must stay excluded from the "stored" side of the diff or they'll be misclassified as delisted every run.
- Keep LLM calls behind a cache keyed on data freshness (e.g. `(ticker, latest_date)`), not just a short TTL — `st.tabs` executes every tab body on every rerun, so an uncached or short-TTL LLM call gets hit far more often than the user's actual clicks would suggest.
- The recommendation flow requires `EXA_API_KEY` (news) in addition to `OPENROUTER_API_KEY` (LLM) — both raise a clear `ValueError` if unset, don't silently fall back.
- Never let a news/LLM failure drop or downgrade the mechanical 매수/매도 action — fall back to a rule-based explanation (`recommendation_engine._build_rule_based_explanation`) instead.
- Don't reintroduce server-side/headless chart image rendering (kaleido etc.) without good reason — v3.0 removed it specifically to stop paying the "CJK font missing on a bare Ubuntu Actions runner" tax; charts are embedded as client-rendered HTML/JS (`fig.to_html()`) instead, in both the Streamlit UI and `report_builder.py`'s report.
- Never let a report-build failure (`report_builder`, LLM/Drive/git push) block the Telegram summary or the recommendation results themselves — same "don't drop what already succeeded" principle as the per-ticker LLM fallback.
- `recommend.yml` needs `permissions: contents: write` to commit+push `docs/reports/{date}.html` for GitHub Pages — don't drop that if the workflow is refactored.
- Always `html.escape()` LLM output and Exa article title/summary text before inserting it into `report_builder.py`'s f-string-built HTML — it's external/untrusted text, and unescaped `<`/`>` would break the page's markup.
- Don't re-fetch news or re-call the LLM for data `recommendation_engine.get_recommendation_for_ticker` already computed — `results[ticker]['news']`/`['text']` should be reused as-is wherever they're displayed (report, Telegram, Streamlit).
- Local `.env` and GitHub Actions Secrets are two entirely separate stores — editing one does not touch the other. After changing a credential locally (e.g. switching `TELEGRAM_CHAT_ID` from a 1:1 chat to a group), also run `gh secret set <NAME>` or it silently keeps using the old value in the scheduled workflow. `gh secret list` shows each secret's last-updated timestamp, which is the fastest way to check whether it's actually in sync with a recent `.env` change.
- For a manual `recommend.yml` test run that shouldn't burn Exa/OpenRouter quota, use `gh workflow run recommend.yml -f skip_llm_and_news=true` (also the default when triggered from the Actions tab UI) — see `config.SKIP_LLM_AND_NEWS` above.
- Manual/sample `recommend.yml` runs also default `is_test=true` (`config.IS_TEST_REPORT`, v3.20-v3.22), which appends `_test` to the published report's filename (both Drive and `docs/reports/`) **and** the recommendations JSON's filename (`_recommendations_{date}.json`, v3.22) so a sample publish never overwrites that day's real report or recommendations archive — pass `-f is_test=false` only when intentionally publishing the real thing by hand (e.g. re-running after a failure).
- Never call `paper_trading.open_position`/`close_position` from `collect.yml`/`recommend.yml` or any other cron path — those are the two mutation points the "모의 투자" feature deliberately restricts to the Streamlit UI (v3.21); the cron only ever reads positions (`load_positions`/`compute_position_returns`) to include in the report/Telegram summary.
